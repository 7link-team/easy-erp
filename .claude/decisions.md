# Decisions

## 物料候选与业务资料
Decision: 单独 material_options 表，仅提供候选，业务继续保存字面值与历史快照。
Reason: 用户明确允许删除只影响列表；避免批量改动库存单位和历史资料。
Alternatives Considered: 业务全部关联可变字典 ID，改名自动同步。
Tradeoffs: 纠正物料实际值必须从物料编辑，候选改名不会自动修复现有物料。
Scope: 规格、类型、单位。
Status: 用户授权设计关联影响处理，实施方案已说明。

## 单据类型
Decision: 沿用 sales_catalog，开单手输在命令事务内新增；必须明确是否计款；已停用类型拒绝新用，管理修改限管理员。
Reason: 复用现有 ID/规则与历史快照，避免名称猜测财务行为。
Scope: 本次单据类型可输入要求。
Status: 实施。

## 导航
Decision: 客户与基础资料独立一级菜单，基础资料内采用共享字典管理器（2026-10-10 后续用户明确要求按 v2 原型恢复左清单右表格，替代早期水平 Tab）。
Reason: 用户要求减少层级；客户原文无深层设计限制。
Scope: 客户、基础资料、库存快捷开单。
Status: 实施。


## 2026-10-10 设计收尾与登录
Decision: 开发代理显式保留 Host，继续沿用服务的 Origin 校验；浏览器经过代理登录作为回归场景。
Reason: 原 Vite 字符串代理重写 Host，真实浏览器登录失败，而无 Origin 的 API 脚本误判成功。
Alternatives Considered: 放宽服务来源校验或删掉 Origin；均不采用。
Tradeoffs: 反向代理须保持外部 Host 与 Origin 一致。
Scope: vite.config.ts、开发代理 E2E。
Status: 已实现并验证。

## 2026-10-10 侧栏与工作台反馈
Decision: 桌面侧栏只让 nav 滚动，品牌标题与底部说明固定；开单发货复用 task-card，并入工作台常用操作网格。
Reason: 用户反馈侧栏标题随菜单滚动、开单按钮设计不协调。
Alternatives Considered: 标题使用 sticky、保留独立开单按钮；现有 flex 侧栏与任务卡片可直接复用。
Tradeoffs: 电脑宽屏四个入口同排，手机两列；按现有权限显示入口。
Scope: App、现有样式和相关 UI 回归。
Status: 已实现，真实浏览器截图及 Chromium / WebKit 相关测试通过。

## 2026-10-10 表单与逐行选料
Decision: 开单在明细列表末尾“添加一行”，新行内选择物料后聚焦数量；不采用固定页脚添加入口或独立批量选料弹窗。
Reason: 用户明确要求连续加行、就地填写，避免长单据上下往返。
Alternatives Considered: 页顶物料按钮列表、固定底部批量选择，均被用户否定。
Tradeoffs: 一次选择一个物料，已选物料禁用，数量在原行修改。
Scope: SaleEditor、现有 Popover 和共享表单样式。
Status: 已实现，11 行与手机交互回归通过。

## 2026-10-10 自定义角色与模块权限
Decision: 用户明确授权本轮实现。新增 roles 表与 roles_v1 迁移，users.role 继续保存角色 ID；admin 为受保护系统身份。角色权限由后端目录统一提供，前端按目录显示模块动作并选中依赖权限，后端独立校验。账号创建/维护、角色维护与主机操作仍限管理员。
Reason: 允许用户维护实际岗位角色，避免仅用三个库存复选框描述全部业务。普通角色不能通过角色维护升级为系统管理员。
Alternatives Considered: 仅新增前端权限复选框无法防止 API 越权；覆盖旧账号权限会改变历史授权，均不采用。
Tradeoffs: users 的历史列及旧 worker/viewer API 兼容；升级将 worker 八种组合分别映射为可维护角色，viewer 始终只读；保留原来的本人单据范围。角色变更撤销成员会话。已关联账号的角色须先转移成员才能删除。
Scope: 物料、物料字典、收发库存、操作记录、清点、销售单据、客户、业务资料、资金账户、财务报表。业务删除沿用停用/作废，退款为独立授权，修订/退货/作废产生退款同样检查退款权限。角色数据纳入完整备份，旧备份在临时副本迁移后恢复。
Status: 实现中，正在进行迁移、直接 API 鉴权与浏览器验证。

## 2026-10-10 统一收发与财务分区
Decision: 入库/出库与开单共用 ItemPicker 和 document.css；明细列表末尾添加一行、行内更换/删除，固定标题和最终操作；入库允许零库存，出库和销售禁止选择零库存。财务按用户确认采用同页三分区。
Reason: 用户确认库存跳转已带入物料，但原两栏布局导致不易辨认；统一编辑方式并明确业务分区。财务减少二级 tab 切换。
Scope: 表单结构、间距、选料行为及财务展示；保留业务事务与预选参数。
Status: 实现并回归中；更正流水无可选记录时禁用并说明原因，只列未冲销原流水。

## 2026-10-10 原型结构对齐
Decision: 用户指出基础资料及多处结构未按 v2 原型实施，现以 prototype.html 为布局依据。基础资料为左清单/右账册/底部新增；客户及单据以真实字段列展示；列表表格消除重复边框和水平内边距。手机字典横向选择、行内字段和操作，列表只保留一层内容留白。
Reason: 仅套用主题令牌不代表页面结构符合设计。通过参考与实装截图以及实际边距测量核对。
Alternatives Considered: 继续保留水平标签和拼接文字行，用户明确否定。
Tradeoffs: 不复制原型占位数或未实现的导入/拖拽等动作，不改变物料候选删除和历史快照规则。保留用户已明确批准的逐行选料、财务同页分区和自定义角色。
Scope: 已有页面的布局/可访问性及回归验证，不增加新的业务模块或修改财务规则。
Status: 已实现，浏览器回归中。

## 2026-10-10 原型与原始业务需求的优先级
Decision: 原型决定视觉布局，不自动成为新增会计或考核规则的依据。用户对新增目标管理提出质疑后，重新核对 20261009.md：要求业绩归属，没有销售目标。成本和目标扩展暂停，尚未修改模型或代码。
Reason: “全部做到位”应是完整实现真实要求，不能把原型演示字段推断成客户未要求的新系统。现金实收与应收必须区分，历史记录不可随现值变化。
Scope: 暂不实施成本算法/目标考核；继续现有业务功能缺口与原型视觉对齐。
Status: 按用户最新纠正执行；成本是否继续及核算口径尚未确认，其他工作继续。
