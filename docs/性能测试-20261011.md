# 大数据量性能测试（2026-10-11）

## 结论

**当前版本不能通过 10 万 / 30 万销售单规模的容量验收。** 已实际完成独立合成库的 HTTP 测量、浏览器验证和有限并发写入检查。主要问题是开单候选加载、财务与工作台汇总、列表长尾及备份容量；不能因为功能测试或 GitHub Actions 通过，就承诺这个数据规模下使用顺畅。

写入正确性检查通过：8 并发开单、幂等重放、超卖拦截、单笔金额和最终库存核对均未发现错误。这只覆盖本轮场景，不代表长期高并发或所有历史数据组合已经验证。

本轮交付测试脚本、证据及报告；业务代码尚未实施性能优化。

## 环境与方法

- 被测提交：`8487721209c72c4baac7041131f6e18c82aefd65`，真实 Rust release 优化构建，嵌入已构建前端。
- 二进制 SHA-256：`e677577e4167ecf1b40b0659d93551db313e4b294f888aadc100fcb68192e78c`。
- 机器：Intel i7-8850H 2.60 GHz、12 逻辑 CPU、16 GiB 内存、macOS 15.7.5；测试目录位于内置 PCIe SSD / APFS。
- 使用独立 `tmp/performance-*` 数据目录及端口 4297；小库浏览器校验使用 4298。现有业务数据库未用于造数或压测。
- 真实服务完成数据库迁移、管理员和标度校验单初始化，再离线 SQL 造数。被测业务操作全部走 HTTP。
- 计时包含本机 HTTP、响应接收和 JSON 解析。单接口通常 5 次；慢接口通常 3 次；请求到达 45 秒测试上限后停止该项并重启测试服务，清理仍可能执行的查询。备份单独设置 60 秒上限。
- 仅在合成库更新定时备份成功时间，隔离自动备份对基线的影响；随后通过真实 API 单独测手动备份。
- 未清除操作系统缓存，非磁盘冷测；本机仍有其他开发服务，非专用压测机。小样本不能用于承诺 SLA，原始 JSON 的 `p95_ms` 在这些样本量下接近最大值。
- 并发来自同一管理员会话，混合阶段为 16 个请求的有限突发；不是 8 个独立用户的持续负载，也不是稳态 QPS 或 24 小时耐久测试。

## 数据集

这里的“10 万 / 30 万”指销售单数量。各档固定 1 万物料、1,000 客户、10 部门、100 业务员。每单 3 行，日期跨度 365 天；90% 已确认、10% 草稿、80% 有收款、5% 有部分退货。每行 1 件、单价 100 元，整单 300 元；收款单实收 150 元，退货单首行退 0.5 件、抵减 50 元。

| ------: | ------------------: | -------: | -------: | ------: | -------: | ---------: |
|  10,000 |              30,000 |    8,000 |      500 |  19,500 |   37,500 |      95.68 |

每张单另有一条合成历史快照、审计和幂等记录。造数后检查 SQLite 完整性、每行单价乘数量与金额一致、全部库存流水与当前余额一致。测试阶段还会新增少量验证单据。

数据是确定性的循环分布，不等同于生产客户分布。未覆盖十万物料档案、照片容量、大量反复修订和全部会计边界组合；真实照片和更多历史修订可能增加负担。

全量单据导出：1 万档约 2.81 秒成功；10 万与 30 万档分别约 6.22 / 10.00 秒返回 HTTP 400，提示超过 50,000 张、需要缩小范围。这是现有限制生效，不能算大库全量导出成功。

| 服务进程采样峰值 RSS，MiB         |  78.06 |   319.35 |   899.18 |

混合读取为单据首页、物料搜索、单号搜索、库存流水各 4 次，均返回 200。RSS 包含各 API 阶段及独立备份，不含浏览器、Python 和系统文件缓存；为 0.5 秒间隔采样最大值。

三个规模均核对通过：

- 新物料库存 8 件，8 张各 1 件的并发开单均成功，第 9 张返回 409；余额为 0。
- 原请求幂等重放得到同一单据，不重复扣库。
- 新单应收 100 元、实收 50 元、欠款 50 元；预设退货单应收 250 元、实收 150 元、欠款 100 元。
- 两个财务查询同时执行时，前台开单均实际持久化；最终负库存数 0、库存差异数 0，SQLite 完整性 `ok`。

两报表争用阶段：1 万档两个报表约 4.5 秒完成；10 万和 30 万均达到这一阶段的 20 秒测试上限。未观察到前台 500 或超卖，但不能据此保证长期稳定。

**只有 1 万档完成了财务 HTTP 全量汇总与预设总额核对。** 10 万和 30 万财务超时，没有完成它们的全量财务 HTTP 校验。

## 备份与恢复容量

| 规模    | 手动备份实际结果                                                                           |
| ------- | ------------------------------------------------------------------------------------------ |
| 1 万单  | HTTP 200，10.82 秒，ZIP 99,488,219 字节，无照片                                            |
| 10 万单 | HTTP 400，15.98 秒，提示“数据库（含凭证图片）超过当前 512 MB 备份上限，请联系管理员扩容。” |
| 30 万单 | 到达 60 秒测试上限，未取得完成响应                                                         |

源码 `backup.rs:29` 的 `MAX_SNAPSHOT` 为 512 MiB，`backup.rs:137` 先执行 `VACUUM INTO` 完整复制，`:141` 才检查大小；恢复路径 `:445` 也有此限制。30 万库同样明显超过源码限制，但本次测量没有实际收到其 400 响应，不能编造成已返回失败信息。

这是可靠性阻断项：10 万库已经无法通过现有内置备份路径完成备份，且尚未完成大库恢复性能验收。后续需要同时验证备份、校验、打包、恢复和故障中断，不能仅放大常量就认定解决。真实凭证照片会进一步增加体积。

## 复现与原始证据

在仓库根目录、已有 Node / Rust 依赖和 Playwright Chromium 的环境运行：

```sh
npm run build
cargo build --release -p easy-erp-server
python3 scripts/performance.py --sizes 10000 100000 300000 --items 10000 --port 4297 --timeout 45
```

脚本打印新建的 `RESULT_DIR`，随后将下面路径替换为本次输出，顺序运行浏览器测量：

```sh
node scripts/performance-browser.mjs tmp/performance-xxx/100000
node scripts/performance-browser.mjs tmp/performance-xxx/300000
```

首次小规模校验可用 `--sizes 1000`。脚本新建独立目录、拒绝占用端口；浏览器脚本仅允许合成性能数据目录。测试库和日志体积较大，均留在忽略目录中，不提交数据库或构建产物。完成后测试服务已停止。

本次正式证据位于本地 `tmp/performance-1x8ofii5/`：

- `metadata.json`：提交、二进制哈希、平台、参数。
- `10000/results.json`、`100000/results.json`、`300000/results.json`：原始样本、HTTP 状态、资源采样、查询计划、正确性和备份结果。
- `100000/browser-results.json`、`300000/browser-results.json`：浏览器等待结果、API 响应时刻及页面错误。
- 两个大库目录内的 `browser-sales.png`、`browser-invoice.png`、`browser-finance.png`：实际页面截图。
- 构建与执行日志：`/tmp/erp-perf-build.log`、`/tmp/erp-perf-release.log`、`/tmp/erp-performance-final.log`、`/tmp/erp-perf-browser-100000.log`、`/tmp/erp-perf-browser-300000.log`。

首轮 `tmp/performance-i7s28356` 因造数单价标度错误、逐行金额不一致，以及未隔离自动备份而作废，其 metadata 已标明不得用于验收。修正后先以 `tmp/performance-m84r0xkn/1000` 验证金额、库存和真实备份成功，再重跑以上正式三规模；本报告不使用作废轮次的耗时。
