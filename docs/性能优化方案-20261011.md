# 大数据量优化方案与评审

## 目标与边界

针对《性能测试-20261011.md》已复现的 10 万 / 30 万销售单瓶颈实施优化。保持 SQLite、现有 API 鉴权、整数金额、退货分摊、修订历史和备份 ZIP 格式；不新增会计口径、不删除历史、不以过期缓存换取速度。

执行模式为 Direct：主代理实施和验收；Claude CLI 只读评审方案及最终关键代码。用户已授权“评审没问题就执行”，评审阻断项须先修正，不重复请求实施许可。

## 设计

### 1. 索引与列表

新增仅含索引的迁移：退货按单据、销售按全局时间/经办人/客户/业务日期、审计排序/经办人/动作、资金账户及日期排序。索引遵循当前 created_at DESC,id ASC 的稳定排序。动态组合已启用的筛选条件，避免默认 OR 参数迫使扫描大 JSON；先从索引取得一页 ID，再读取该页完整记录。保留页码、总数、当前搜索含义及权限过滤。

评审期间的只读 SQL 探针显示，直接聚合仍可能被客户索引引导为大量随机读取（30万档约71秒）。因此还需针对报表实际选取的状态、业务日期、客户、历史归属及金额建立覆盖表达式索引；以 EXPLAIN 和实测选择查询方式，不假定 JOIN 天然更快。新增索引的大小及写入成本列入复测。

性能迁移不改变备份业务结构版本；恢复保留现有目标索引，旧备份仍按原业务 schema 判定并迁移。不得修改已发布迁移。

大库首次升级需要实际建立索引。桌面启动原有约10秒窗口会提前终止仍在迁移的服务，因此同步将自有进程启动等待上限扩为10分钟，并继续检查进程退出及服务身份；测试工具使用相同启动窗口。用旧30万库副本验证升级，记录建立索引与启动耗时、升级前后业务表指纹。

### 2. 开单候选与资料管理

增加明确的轻量候选读取模式，业务表单只读资料，不做历史引用统计。保留原管理接口的 usage_count/can_delete 语义及删除时事务内重新检查；轻量模式不声称资料可删除。部门成员用一次聚合代替逐候选扫描。管理引用统计将同一历史 JSON 的字段展开合并，减少重复扫描。

先覆盖现有 1 万物料、1000 客户的压测口径。候选搜索沿用现有接口的 50 项上限；不把当前项目改造成全新选择器体系，也不声称已支持十万客户或物料。

### 3. 财务与工作台

建立复用的 SQL 余额投影：按 sale_id 预聚合收款和退货行 credit，再连接单据。应收严格为 posted 时 total 减退货行 credit 合计，其他状态为零；实收沿用带符号收退款流水合计。查询处使用同一读事务。

财务按客户/业绩归属/日期批量聚合，工作台按日期/归属聚合，仅读取需要展示的明细。工作台今日单据单独聚合全部可见状态的类型/数量及带符号收款，应收只计 posted；完整单据只取最近6张，不能套用只含posted的财务投影后丢掉草稿/作废计数。月度物料分类只展开本月历史单据行，沿用 Rust 分类 key 规范化，不能从当前物料倒填。全部期间继续包含未来业务日期，月/季/年截止今天，欠款账龄沿用原规则。无单据业务员、当前改名和历史归属继续保留。

账户流水通过独立 `/sales/cash` 接口增加服务端筛选、每页 50 条、筛选总数和完整筛选金额汇总；页面翻页不能改变汇总。财务汇总请求可显式省略明细，页面按需读取流水，避免每次返回几十万行。既有 finance 调用的默认明细语义保留，所有仓库页面显式省略，避免静默截断旧调用。对账 CSV 必须导出完整筛选结果，不能仅导出当前页，复用现有后端导出和 50,000 条限制；新流水和导出路径均要求 finance.read，不错误套用已有导出的 admin 权限，也不能放宽其他导出权限。

### 4. 大库备份与恢复

将快照/恢复安全上限统一提升到 16 GiB，以覆盖当前约 2.7 GiB 库并保留解压大小保护。复制前检查预计大小及可用磁盘空间，仍以实际快照/解压字节数复核。ZIP 使用 ZIP64 标记，保留格式版本、校验和及原后缀兼容性。下载复用 tower-http 文件服务流式输出，不将完整文件放入内存。

销售备份校验分批读取单据、批量取相关收款/退货及必要资料，逐行复用现有金额与退货验证规则，不能删减校验。库存对平改为聚合连接。安全临时目录、完成后发布归档、恢复前安全备份、恢复事务、注销会话保持有效。分阶段记录耗时，失败不发布半成品。恢复前先检查包含安全备份和事务空间的保守空间余量，实际 I/O 错误仍正常传播。

空间预检采用备份 `3×当前库页数×页大小+256MiB`（快照、Stored ZIP及写入余量）；恢复 `4×当前库大小+2×解压库大小+256MiB`（解压副本、安全备份快照/归档、恢复事务和写入余量）。这是保守预检，不是磁盘预留，后续I/O错误仍中止操作。复用已安装的fs2与tower-http/fs，无需新增依赖。记录复制、校验、发布阶段耗时及测试目录分配块大小的采样峰值。大于512MiB的新归档不保证向旧版本降级恢复；本轮不新增断点续传功能。

## 涉及文件

- 后端：`migration.rs`、`sales.rs`、`dashboard.rs`、`inventory.rs`（本轮只改审计查询，原库存流水首页已通过基线）、`transfer.rs`、`backup.rs`；余额投影直接在sales模块复用。
- 前端：`src/pages/Sales.tsx`、`src/sales.ts`，复用现有分页、请求和导出组件。
- 桌面：`desktop/src/desktop.rs` 调整首次迁移的启动等待；`desktop/src/updates.rs` 将备份停止请求的120秒等待延长至30分钟（与大库备份测试上限一致），保留失败中止与恢复标记。
- 验证：相关财务/权限/历史/备份 E2E、`scripts/performance*.{py,mjs}`及报告。
- 无新增运行时依赖、无数据库替换、无金额算法或账号权限变更。

## 风险与验收

1. 金额正确性优先：对照单据详情逐笔汇总，覆盖部分退货、退款、更正冲销、优惠、非计款、草稿/作废、未来日期、旧分类快照、历史归属及零业绩人员。
2. 分页前后总额一致，筛选与导出一致；权限不因 SQL 改写扩大。
3. 旧库迁移成功，旧 ZIP 可恢复；大库实际备份、流式下载校验、恢复后的金额/库存/关键行数一致；损坏 ZIP 拒绝且原库不变。
4. 复用正式基线相同生成分布，另建新库，保留原始证据。10 万/30 万常用列表、轻量候选和详情目标中位 <1 秒，浏览器可用内容目标 <3 秒；财务/工作台目标 <3 秒，8 并发混合读取无错误。全文搜索继续匹配全部历史 JSON 文本（计数与分页各一次扫描）、资料管理继续计算完整历史引用，两者单列实测中位/最大耗时，不承诺普通B-tree索引能够令它们低于1秒。留存报表覆盖索引EXPLAIN原文；旧ZIP恢复后还要验证财务和工作台返回200。阈值为本机工程验收目标，不是生产 SLA。
5. 大库备份恢复单独记录完成时间、峰值内存和磁盘需求，不套用交互页面 3 秒目标。上轮 60 秒上限不足时明确延长测试窗口，不把超时当成功。
6. 如未达到目标或波动仍明显，继续针对证据定位；不得只报平均值或宣称容量全面通过。保留原三规模对照、浏览器截图及一致性结果。
7. 保留既定每小时备份与按天保留策略，不新增按份数/字节提前删除历史的规则。30万库每份约数GiB，按现有7天每小时保留可能需要数百GiB磁盘；部署容量必须按实际归档大小测算。空间不足应拒绝新备份并通过现有 last_error 明确提示，保留已有完整备份。容量优化不代表现有120GiB测试盘适合该规模7天生产保留。
